# Звіт до самостійної роботи №6

## Сценарій 1: система сповіщень

### Обраний підхід: інтерфейс `INotifier`

Для Email, SMS і Push головне спільне — можливість виконати дію `Send(string message)`. Вони не потребують спільного стану або готової реалізації методу. Тому інтерфейс підходить краще: він задає контракт, але не нав'язує спільну базову реалізацію.

Абстрактний клас тут був би менш доречним, тому що спільної логіки майже немає. Крім того, інтерфейс залишає класам можливість успадковуватися від іншого базового класу.

```csharp
public interface INotifier
{
    void Send(string message);
}
```

У `Main` створено `List<INotifier>` з трьома різними реалізаціями, після чого один цикл викликає `Send()` для кожної з них.

## Сценарій 2: обробка файлів

### Обраний підхід: абстрактний клас `FileProcessor`

Для обробників файлів є не тільки спільний контракт, а й спільний алгоритм: відкрити файл, обробити вміст, закрити файл. Тому абстрактний клас дозволяє винести однакові кроки в базовий клас, а конкретним класам залишити тільки унікальну частину.

```csharp
public void Process()
{
    OpenFile();
    ProcessContent();
    CloseFile();
}
```

Метод `ProcessContent()` є абстрактним, тому `TextFileProcessor` і `XmlFileProcessor` реалізують його по-різному.

Якби тут використовувався лише інтерфейс, кожному класу довелося б окремо реалізовувати відкриття та закриття файлу, що створювало б дублювання.

## Загальний висновок

Інтерфейс доцільно використовувати, коли різним класам потрібен спільний контракт без спільного стану та реалізації. Абстрактний клас зручніший, коли об'єкти мають спільні дані або частину готового алгоритму. В обох сценаріях поліморфізм дозволяє працювати з різними реалізаціями через один базовий тип.
